# WAPTrix

**Passive Web Application Security Auditing & OWASP Top 10 (2025) Compliance Platform**

WAPTrix is a strictly passive web application security auditing framework modeled after **Burp Suite's Passive Audit**. Give it a list of authorized subdomains and it performs non-intrusive HTTP/TLS inspection. Every finding is mapped to **CWE**, **OWASP WSTG v4.2**, **CVSS v3.1** and the **OWASP Top 10 (2025)**. You get a compliance dashboard broken down by subdomain, plus reports you can export.

> **Passive by default.** Out of the box WAPTrix sends only read-only HTTP `GET` requests (to `/`, `/robots.txt` and `/.well-known/security.txt`) and standard TLS handshakes — it does **not** fuzz, inject payloads, forge `Origin` headers, brute-force, authenticate, or request paths it discovers. Active engines (Nmap, Nuclei, Nikto, Wapiti, sqlmap, ZAP active) exist as an **explicit opt-in** that additionally requires scope domains and a written-authorization attestation (see [Assessment workflow](#assessment-workflow-s1s6)). Only audit systems you are explicitly authorized to test.

## Key Features

- **Subdomain-wise visibility.** Audit dozens of subdomains concurrently. For each one you see its HTTP status, TLS posture, captured headers, compliance grade (`A`–`F`), and raw evidence.
- **OWASP Top 10 (2025) compliance matrix.** An interactive **Subdomain × Category** heatmap (`Pass` / `Warning` / `Fail` / `Manual Review`). WAPTrix marks categories that cannot be verified passively as `Manual Review` instead of passing them by mistake.
- **45 Burp-style passive rules** in 7 modules:
  - **Security headers:** `CSP` (missing / unsafe sources / report-only), `HSTS` (missing / short max-age), `X-Frame-Options` / `frame-ancestors`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`.
  - **Transport & TLS:**
    - no HTTPS, or no HTTP→HTTPS redirect
    - deprecated protocols (negotiated, or accepted by a capped TLS 1.1 ClientHello)
    - weak ciphers
    - certificates that are expired, about to expire, mismatched to the hostname, or untrusted
    - active and passive mixed content
  - **Cookie hygiene:** missing `Secure`, `HttpOnly` (with session-cookie awareness), `SameSite`, `SameSite=None` without `Secure`, and parent-domain scoping. Cookie values are redacted in evidence.
  - **CORS & caching:** wildcard origin with credentials, `null` origin, wildcard origin, and sensitive responses that do not send `Cache-Control: no-store`.
  - **Information disclosure:**
    - version banners in `Server`, `X-Powered-By` and similar headers
    - stack traces (Python, Java, .NET, PHP, Node, Ruby, Go, SQL)
    - debug modes (Django, Werkzeug, Laravel, Symfony, Rails and others)
    - sensitive HTML comments, private IP addresses and email addresses
  - **Client-side & forms:**
    - passwords submitted in cleartext, and insecure form actions
    - POST forms without anti-CSRF tokens, and password autocomplete
    - missing SRI on third-party scripts and stylesheets
    - **vulnerable JS library fingerprinting** (jQuery, jQuery UI, AngularJS, Bootstrap, Lodash, Moment, Handlebars, Underscore, Vue 2, DOMPurify, Axios)
  - **Security metadata:** `security.txt` (RFC 9116) that is missing, invalid or expired, and sensitive `Disallow` entries in `robots.txt`.
- **Declarative scope guard.** It enforces:
  - a mandatory authorization reference
  - host normalization and deduplication (IDNA, ports, URLs)
  - wildcard rejection and an optional allowlist of scope domains
  - **private, loopback and link-local IP protection after DNS resolution**
  - redirects followed only on the same host, and a per-host rate limit
- **Multi-format reporting.** Export the **full engagement** or a **single subdomain** to **PDF** (WeasyPrint, with an automatic print-ready HTML fallback), **HTML**, **JSON**, **CSV** (protected against formula injection) and **SARIF 2.1.0** (for GitHub Code Scanning and CI).
- **Offline demo mode.** A realistic dataset of 5 subdomains (`*.acme-corp.example`), generated by running the real engine against mocked responses.

## Quick Start

### Option A: Docker Compose (recommended, includes the external tools)

**This is the only path that ships all ten tools.** Images are built locally, so each machine gets a native build (x86-64 or ARM64). It works identically on macOS, Windows and Linux — the only difference is how you install Docker and generate the key (see [Running on macOS, Windows and Linux](#running-on-macos-windows-and-linux)).

```bash
git clone https://github.com/Kratos-sec/WAPTRIX.git
cd WAPTRIX
cp .env.example .env                 # then set ZAP_API_KEY (see per-OS commands below)
docker compose up --build -d
```

Open `http://localhost:8080`. The API is proxied at `http://localhost:8080/api`. Only that port is published, and only on `127.0.0.1`.

> **The "not installed" question.** The **New audit** panel reports each tool as available only if the *backend answering `/api/tools`* can find it. The Dockerised `api` (Kali base) has all ten, so on `http://localhost:8080` every tool shows a version. If you instead open the Vite dev server (`http://localhost:5173`) or a hand-run `uvicorn`, the panel reflects whatever is on **that machine's** PATH — usually only what you installed with Homebrew/apt — and everything else reads *not installed*. That is expected: use `http://localhost:8080` for the full tool belt, or point the dev proxy at the container (`WAPTRIX_API=http://127.0.0.1:8080 npm run dev`).

| Service | Contents |
| --- | --- |
| `api` | FastAPI backend plus the tool belt (Kali point-release base): Nmap, WhatWeb, Nikto, Wapiti, sqlmap, testssl.sh, Nuclei, Retire.js, SSLyze. Runs as an unprivileged user |
| `zap` | OWASP ZAP 2.17 in daemon mode, reachable only inside the stack, protected by `ZAP_API_KEY` |
| `web` | nginx serving the built dashboard |

Check what is installed: `curl localhost:8080/api/tools` or `docker compose exec api waptrix tools`.

Notes:
- ZAP needs 2–4 GB of memory. On Docker Desktop, give the VM at least 4 GB.
- To audit an app running on your own machine, target `host.docker.internal`.
- Data lives in the `waptrix-data` volume. `docker compose down -v` deletes it.

### Option B: Local install (built-in checks only)

#### Prerequisites

- **Python 3.11+**
- **Node.js 18+** and `npm`
- *(Optional, for native PDF)* the Pango libraries that WeasyPrint needs:
  - macOS: `brew install pango`
  - Debian/Ubuntu: `apt install libpango-1.0-0 libpangoft2-1.0-0`

  Without them, PDF exports fall back to a print-ready HTML report.

#### 1. Backend

```bash
git clone https://github.com/Kratos-sec/WAPTRIX.git
cd WAPTRIX/backend

python3 -m venv .venv
source .venv/bin/activate            # Windows: .venv\Scripts\activate
pip install -r requirements.txt
pip install -e .                     # optional: installs the `waptrix` command
```

#### 2. Run the API

```bash
uvicorn app.main:app --reload --port 8000
# or: waptrix serve --port 8000
```

The API is at `http://localhost:8000`, with Swagger docs at `http://localhost:8000/docs`.

#### 3. Run the dashboard

Run this in a second terminal:

```bash
cd WAPTRIX/frontend
npm install
npm run dev
```

Open `http://localhost:5173`. Vite proxies `/api` to `127.0.0.1:8000`; override the target with `WAPTRIX_API=http://host:port npm run dev`. From there you can:

- click **Load demo** to explore the dashboard right away, or
- click **New audit** to paste subdomains or upload a `.txt` file.

**Single-process deployment:** run `npm run build` in `frontend/`. FastAPI then serves `frontend/dist` at `http://localhost:8000/`.

## Running on macOS, Windows and Linux

Docker Compose (Option A) is the same three commands everywhere; only the setup around it differs. Pick your platform.

### Common prerequisites (all platforms)

- **Docker** with the Compose plugin (`docker compose version` ≥ 2.0). Docker Desktop on macOS/Windows, Docker Engine on Linux.
- **Give the Docker VM ≥ 4 GB RAM.** ZAP and WebGoat are JVM apps; with less, the VM OOM-kills them. Docker Desktop → Settings → Resources → Memory. 8 GB is comfortable if you also run the benchmark lab.
- **Ports:** only `127.0.0.1:8080` is published. Nothing else is exposed to your network.

### macOS

```bash
# 1. Docker Desktop: https://www.docker.com/products/docker-desktop  (or: brew install --cask docker)
# 2. Generate the ZAP key into .env
cp .env.example .env
echo "ZAP_API_KEY=$(openssl rand -hex 24)" >> .env     # or edit .env by hand
# 3. Up
docker compose up --build -d
open http://localhost:8080
```

- **Apple Silicon (M1–M4):** the DVWA, bWAPP and Mutillidae images are amd64-only and run under Rosetta emulation — slower, but they work. The `api`, `web`, `zap`, Juice Shop and WebGoat images are native ARM64.
- Local-install (Option B) only sees Homebrew tools. `brew install nmap sqlmap nikto` covers a few; the rest (wapiti, nuclei, whatweb, testssl, sslyze, zap) are fiddly on macOS — this is exactly why Docker is recommended.

### Windows

Use **WSL2** (Docker Desktop's default backend). Run the commands from a WSL2 shell (Ubuntu), **not** PowerShell, so paths and line endings behave.

```bash
# In PowerShell (admin), once:   wsl --install
# Install Docker Desktop and enable "Use the WSL 2 based engine" + your distro under Settings → Resources → WSL integration.
# Then, inside the WSL2 (Ubuntu) shell:
git clone https://github.com/Kratos-sec/WAPTRIX.git
cd WAPTRIX
cp .env.example .env
echo "ZAP_API_KEY=$(openssl rand -hex 24)" >> .env
docker compose up --build -d
```

Open `http://localhost:8080` in your Windows browser (WSL2 forwards `localhost`).

- **Clone inside the WSL2 filesystem** (e.g. `~/WAPTRIX`), not under `/mnt/c/...` — the Windows mount is slow and mangles file permissions.
- Line endings: the repo ships a `.gitattributes` that forces `LF`, so shell scripts (`lab/bootstrap.sh`) stay runnable. Don't re-checkout with `core.autocrlf=true`.

### Linux

```bash
# Docker Engine + compose plugin (Debian/Ubuntu):
#   sudo apt install docker.io docker-compose-plugin   (or follow docs.docker.com/engine/install)
#   sudo usermod -aG docker $USER && newgrp docker      # run docker without sudo
git clone https://github.com/Kratos-sec/WAPTRIX.git
```

- Native amd64 host: every image runs natively, no emulation.
- If `docker` needs `sudo`, either add yourself to the `docker` group (above) or prefix the commands.

```bash
docker compose ps                                  # all services "running"/"healthy"

curl -s http://localhost:8080/api/tools | grep -c '"available": *true'   # expect 10
```

If `/api/tools` shows fewer than ten, you are hitting a non-Docker backend (see the note under Option A), not a broken install.

```bash

```

## CLI Usage

Run these from `backend/` (use `python -m app.cli …`, or `waptrix …` after `pip install -e .`):

```bash
# Passive audit of authorized subdomains, exporting all formats
python -m app.cli audit \
  --subdomains subdomains.txt \
  --auth-ref "ENG-2026-001" \
  --scope-domain example.com \
  --out ./reports

# Choose formats, tune politeness, export one host only
python -m app.cli audit -s subdomains.txt -a ENG-2026-001 -f pdf,sarif --rate 1 --concurrency 3 --only app.example.com

# Built-in offline 5-subdomain demo (no network)
python -m app.cli demo --out ./demo_reports

# List every rule with its OWASP 2025 / CWE / WSTG / CVSS mapping
python -m app.cli rules

# Show which external tools are installed, with versions
python -m app.cli tools
```

Example `subdomains.txt` (blank lines and `#` comments are ignored; URLs are normalized to hosts):

```
app.example.com
api.example.com
https://admin.example.com/login
static.example.com:8443
```

| Option | Default | Description |
| --- | --- | --- |
| `--auth-ref / -a` | *required* | Engagement or ticket reference (3–64 chars) |
| `--scope-domain` | — | Rejects targets outside these apex domains (repeatable) |
| `--format / -f` | `all` | Any of `json,csv,sarif,html,pdf` |
| `--rate / -r` | `2` | Maximum requests per second per host |
| `--concurrency / -c` | `5` | Subdomains audited in parallel |
| `--allow-private` | off | Permits targets that resolve to private or reserved IPs |
| `--no-metadata` | off | Skips `robots.txt` and `security.txt` |
| `--only` | — | Exports reports for a single subdomain |
| `--tool` | — | Adds an external passive tool (repeatable): `whatweb`, `sslyze`, `testssl`, `retire`, `zap`, or `all`. Needs the Docker stack or local installs |
| `--tool-timeout` | `600` | Time limit per tool, per host, in seconds |
| `--retest-rounds` | `1` | Bounded S5→S3 re-test rounds for candidates below the voting threshold (`0` disables) |
| `--max-endpoints` | `5` | Parameterised endpoints per host that per-endpoint engines (sqlmap) may target |

The API takes the same choice as `"tools": ["sslyze", "zap"]` in the `POST /api/audits` body.

### External passive tools

Each tool runs once per reachable host, after the built-in checks, and only in the ways listed here:

| Tool | What it sends | What WAPTrix takes from it |
| --- | --- | --- |
| WhatWeb | One GET of the page URL (aggression level 1, redirects not followed) | Technology inventory; version banners |
| SSLyze | TLS handshakes for protocol/cipher enumeration, certificate, curves, fallback SCSV, compression. Heartbleed, ROBOT, CCS-injection and renegotiation probes are never scheduled | Deprecated protocols, weak ciphers, trust, expiry, compression, SHA-1 chains |
| testssl.sh | Protocol, server-defaults, standard cipher categories and forward-secrecy sections only. The vulnerability section (`-U`) is never run | The same TLS issues as a cross-check, plus anything else it rates LOW or worse |
| Retire.js | Nothing itself. WAPTrix downloads up to 20 same-host scripts the page already loads, through its own rate-limited fetcher; off-host (CDN) scripts are never fetched | Vulnerable JavaScript libraries with CVEs |
| OWASP ZAP | One GET of the page URL through the ZAP daemon (no spider, no active scan, redirects not followed). The site is removed from ZAP afterwards | ZAP passive-rule alerts |

How results combine:
- Where a tool reports an issue a built-in rule already covers, it maps onto that rule (same severity, CVSS and remediation). If the host already has that finding, the tool is added to the finding's `sources` instead of creating a second one, so agreement between engines does not lower the score twice.
- Tool alerts with no matching rule become `<TOOL>-<id>` findings (for example `ZAP-10015`, `TESTSSL-CERT-REVOCATION`). They carry the tool's own severity and CWE, take their OWASP category from the CWE, and have no CVSS score.
- Every tool run is recorded per subdomain in `tool_runs` (command, exit code, duration, errors). A tool that fails or times out never aborts the audit.

### Assessment workflow (S1–S6)

Every audit runs as the six-stage workflow, and each stage transition is written to a run log:

| Stage | What happens |
| --- | --- |
| S1 Scope & authorisation | Validates the authorisation reference, the in-scope host list and the request budget (rate, concurrency, tool timeout). Nothing runs without them |
| S2 Passive reconnaissance | DNS with private-address guard, read-only GETs, TLS inspection, built-in checks, passive tools |
| S3 Application map | URL tree and parameter inventory (same-host links, forms, scripts) built from the page S2 already fetched, so no extra requests |
| S4 Phase controllers | Active engines run against the map, in parallel under the rate governor. Per-endpoint engines (sqlmap) target each parameterised endpoint, up to `--max-endpoints`. Skipped in passive mode |
| S5 Correlation | Cross-tool voting (eq. 1, τ = 0.55). Candidates below τ go back to S3 with their exact endpoint as a refined hypothesis, and S4 re-runs the active engines that can detect or confirm that class. This repeats for up to `--retest-rounds` rounds and stops early when there is nothing new to try |
| S6 Risk & report | Per-host scoring and grading, then the engagement summary |

The dashboard's **Workflow** tab shows the stage timeline, the voting outcome, the re-test queue, every tool run and the full run log. A running audit shows the S1–S6 stepper and the log live. Each finding card shows its C(f) score against τ, and the engines that detected it, could have detected it, or stayed silent. Each host's drawer adds its S3 application map, tool runs and re-test queue. The New audit panel picks passive tools and, behind an explicit opt-in, active engines and re-test settings.

The result carries `stages` (one summary per stage: hosts, runs, duration, counts) and `run_log` (every event). Each subdomain also gets its `app_map` and `retest_rounds_run`, and each tool run records its `stage`, `round` and `target_url`. The SQLite store keeps the run log in `run_events` and writes it as the audit runs. Tool runs go in `tool_runs`, and below-τ candidates are stored in `findings` with `admitted = 0` and their `correlation_score`.

## Benchmark Lab and Evaluation

The lab reproduces the paper's test bed (Table VI) and scores runs into its Table VII format.

**Test bed.** `docker-compose.lab.yml` adds five vulnerable apps:

| App | Image | Hostname |
| --- | --- | --- |
| DVWA | `vulnerables/web-dvwa` | `dvwa.waptrix.lab` |
| OWASP Juice Shop 17.1.1 | `bkimminich/juice-shop:v17.1.1` | `juiceshop.waptrix.lab` |
| WebGoat 2023.8 | `webgoat/webgoat:v2023.8` | `webgoat.waptrix.lab` |
| bWAPP | `raesene/bwapp` | `bwapp.waptrix.lab` |
| Mutillidae II | `webpwnized/mutillidae` | `mutillidae.waptrix.lab` |

- The apps sit on an `internal` Docker network with no egress and no published ports. Only the `api` and `zap` containers join it.
- An nginx gateway gives every app its own hostname on port 80, so engines start from the application root.
- The older PHP images only ship for amd64. On Apple silicon they run under emulation.

```bash
docker compose -f docker-compose.yml -f docker-compose.lab.yml up -d --build
./lab/bootstrap.sh            # one-time database setup for DVWA, bWAPP and Mutillidae
docker compose -f docker-compose.yml -f docker-compose.lab.yml exec api \
  python -m app.cli lab collect --reps 3 --out /lab/runs/latest
docker compose -f docker-compose.yml -f docker-compose.lab.yml exec api \
  python -m app.cli lab evaluate --runs /lab/runs/latest --out /lab/results/latest
```

**collect** runs the full active workflow (built-in checks, ZAP passive, Nikto, Nuclei, Wapiti, sqlmap, ZAP active) against each app, three times by default.
- Each run record keeps the audit result and every raw pre-correlation finding.
- It refuses to scan unless every lab host resolves to a private address. In practice, that means it only runs inside the lab network.

**evaluate** rebuilds and scores several report sets from the records:
- each engine on its own
- the naive union of the four compared engines
- WAPTrix as run
- WAPTrix re-voted with leave-one-app-out weights: each engine's w_i is its smoothed precision (TP+1)/(TP+FP+2) on the other four apps

Scoring rules:
- It takes the median over repetitions.
- It writes `results.json`, `table.md` (Table VII layout, per-app tables, false-positive suppression) and `table.csv`.
- A finding matches a ground-truth entry by CWE family, URL path and, when given, parameter. Each entry counts once.
- Findings below `min_severity`, and classes listed in `out_of_scope_tags`, are not scored for any system. By default these are TLS, ports, and header, cookie, CORS and metadata hygiene.

**Ground truth** lives in `lab/ground_truth/<app>.json`. The shipped files are seeds, not the paper's full list:
- DVWA lists its core modules, Juice Shop six documented issues, and WebGoat three GET-reachable lessons (SQLi, path traversal, stored XSS). bWAPP and Mutillidae are still empty.
- Each file carries the paper's `documented_total`, and the report flags apps whose ground truth is partial.
- Extend the entries from each project's solution documentation. Record findings outside the list in `lab/adjudication/<app>.json`: a finding counts as a true positive only with verdict `tp` and two distinct reviewers.

Until the ground truth is complete, the numbers are not comparable with the paper's Table VII.

**Authenticated scanning.** `lab/targets.json` carries per-app `seed_urls` (parameterised endpoints added to the application map so injection engines have something to test), and `backend/app/evaluation/lab_login.py` logs in with each app's default credentials and threads the session cookie through the fetcher, Nuclei, Wapiti, sqlmap, WhatWeb and ZAP. So login-gated surface on DVWA, bWAPP and WebGoat is reachable. Known gap: DAST engines detect little on Juice Shop's Angular/REST surface (the documented SQLi does not trip sqlmap's heuristics, and exposure endpoints report only header hygiene) — a real scanner blind spot, not a configuration error.

**Not covered yet:**
- **Seed → active-engine plumbing.** Seeds populate the built-in application map, but ZAP's and Nuclei's own spiders may not visit them, so some seeded endpoints go untested by those engines.
- **WSTG phase coverage** (Fig. 6b) is not computed.

## OWASP Top 10 (2025) Passive Coverage

| Category | Coverage | Examples checked |
| --- | --- | --- |
| **A01: Broken Access Control** | Partial | Permissive CORS, parent-domain cookies, sensitive `robots.txt` paths, missing CSRF tokens |
| **A02: Security Misconfiguration** | High | Missing or weak security headers, version banners, debug modes, `security.txt` |
| **A03: Software Supply Chain Failures** | Partial | Vulnerable client-side JS library versions, third-party scripts without SRI |
| **A04: Cryptographic Failures** | High | TLS < 1.2, weak ciphers, certificate validity, HTTPS redirect, HSTS, mixed content, `Secure` cookies |
| **A05: Injection** | Indicators only | Missing or weak `CSP` and `X-Content-Type-Options`. A clean result shows as **Manual Review** |
| **A06: Insecure Design** | Partial | Insecure form actions, missing anti-CSRF patterns, missing `SameSite` |
| **A07: Authentication Failures** | Partial | Session cookie flags, cleartext password forms, cacheable login pages |
| **A08: Software or Data Integrity Failures** | High | Third-party scripts and styles without SRI, active mixed content |
| **A09: Logging & Alerting Failures** | Manual | Always **Manual Review** (cannot be verified passively) |
| **A10: Mishandling of Exceptional Conditions** | Partial | Stack traces, framework exception dumps, debug error pages |

### Scoring

- **Subdomain score.** Each subdomain starts at **100**. Every unique rule deducts a weight by severity:
  - critical 30, high 15, medium 8, low 3, info 0
  - each repeated instance of a rule adds 25% of its weight, up to 4 repeats
- **Grades:** A ≥ 90, B ≥ 80, C ≥ 70, D ≥ 60, F < 60.
- **Overall score:** the mean of the reachable subdomains' scores.
- **Category status:**
  - `Fail` if the category has any medium or higher finding
  - `Warning` if it has only low findings
  - `Pass` if it is clean (or has only informational findings) **and** passive coverage is high or partial
  - `Manual Review` otherwise, and for unreachable hosts
- **CVSS v3.1 base scores** are computed from each rule's vector using the specification formulas.

## Safety Model

1. **Authorization first.** Every audit needs an authorization reference, and the dashboard also requires an explicit attestation.
2. **Read-only traffic.** WAPTrix sends only `GET` requests with a clear `WAPTrix-Passive` User-Agent, reads at most 1.5 MB of each body, and caps redirects at 5. It never follows a redirect to another host.
3. **Network guardrails.** Targets that resolve to private, loopback, link-local, CGNAT or reserved addresses are skipped unless `allow_private` is set. Wildcards are rejected, and an optional allowlist of scope domains limits the targets.
4. **Rate limiting.** One shared limiter per host covers both HTTP requests and TLS handshakes.
5. **Evidence hygiene.** Cookie values are redacted. Paths listed in `robots.txt` are reported but never requested.
6. **External tools stay passive.** Only tools whose registry mode is passive can be selected; requests naming an active tool are rejected. Tools are started without a shell, with a hard time limit that kills the tool's whole process group.
7. **Secrets.** The ZAP API key is read from `.env` (git-ignored) and sent only in the `X-ZAP-API-Key` header, never in a URL, so it cannot appear in error messages, tool-run records or reports.
